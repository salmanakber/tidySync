# Project Context — TidySync (AI-Guided Bulk Data App for Shopify)

**App name: TidySync.** Use this consistently across the codebase — package/repo names,
env var prefixes, DB naming conventions, UI branding text, code comments referencing
the product, etc. Sister app to TidyFlow (tidyflowapp.com); no separate domain purchase
planned — served from a subdomain (e.g. `sync.tidyflowapp.com`), not its own top-level domain.

## 1. What we're building

A Shopify app that lets merchants bulk import/export/edit store data (products, variants,
inventory, collections, metafields, etc.) through a **simple, AI-guided interface** instead
of raw spreadsheet column-mapping. Direct competitor: **Matrixify** (apps.shopify.com/excel-export-import).

Our wedge is NOT feature parity. It is:
- Natural-language bulk operations ("increase all Summer Collection prices by 10%")
- A visible diff/preview before any write happens
- One-click undo via snapshots
- AI-assisted column mapping and error auto-fix on import
- Advanced power (bulk AI content rewrite, catalog health scan, anomaly detection)
  hidden behind a UI a non-technical merchant can use in under 10 minutes

Two separate surfaces ship from one codebase/monorepo:
1. **Embedded Shopify Dashboard** — lives inside Shopify Admin (iframe, App Bridge), used
   by the merchant day-to-day: import/export, AI bulk edit, job history, undo.
2. **Internal Admin/Control Panel** — separate, NOT embedded in Shopify, used by us
   (the app operators) to manage tenants, plans/billing, feature flags, support tools,
   job monitoring across all stores, and system health.

## 2. Tech stack

| Layer            | Choice                                                              |
|-------------------|----------------------------------------------------------------------|
| Frontend (both apps) | Next.js (App Router), TypeScript                                 |
| Embedded UI        | Shopify Polaris + App Bridge (inside Shopify Admin iframe)         |
| Internal admin UI  | Next.js, plain React (no Polaris constraint), our own design system|
| API layer          | GraphQL (Apollo Server or Yoga) — single API serving both frontends|
| Database           | PostgreSQL (primary datastore for jobs, snapshots, tenants, plans) |
| Queue/background jobs | BullMQ + Redis (large import/export/undo jobs run async)        |
| Shopify data access | Shopify Admin GraphQL API (never REST unless something is GraphQL-only) |
| AI layer            | LLM calls for: NL→mutation-plan parsing, column-mapping inference, content rewrite, catalog health scan. Start on cheaper/free-tier providers, swap to managed APIs as volume grows. |
| File processing     | Streamed CSV/XLSX parsing (do not load full file in memory — support large catalogs) |
| Hosting             | VPS-first, lean/cost-conscious. Avoid over-provisioned managed infra until usage justifies it. |
| Auth (embedded app) | Shopify OAuth + session tokens (standard Shopify app auth flow)   |
| Auth (internal admin) | Separate auth system — email/password or SSO for our internal team only, fully isolated from merchant auth |

**Key principle**: the GraphQL API is the single source of truth for both frontends.
The embedded dashboard and the internal admin panel are two separate Next.js apps
(or two route groups in one Next.js app — decide based on deploy needs) that both
talk to the same GraphQL layer, scoped by role/tenant.

## 4. Core data model (Postgres — draft, refine during schema design)

- `tenants` — one row per installed Shopify store (shop domain, plan, install date, status)
- `users` — internal admin users only (merchants authenticate via Shopify session, not this table)
- `jobs` — every import/export/bulk-edit run (type, status, tenant_id, row_count, started_at, finished_at, error_summary)
- `job_snapshots` — pre-change state captured per job, used for undo (tenant_id, job_id, resource_type, before_state JSONB)
- `job_line_items` — per-row/per-record result within a job (success/fail/skipped, reason)
- `ai_operations` — log of NL prompt → generated mutation plan → user-approved/edited version (for audit + improving prompts over time)
- `plans` — pricing tiers and limits
- `audit_log` — who (which tenant/user) did what, when — for both merchant-facing history and internal support visibility
- `platform_field_maps` — config-driven field mapping definitions per source platform/version (see section 6), reusable across tenants as defaults and per-tenant as saved custom mappings

## 5. Feature scope reference (see roadmap for phasing)

**Note on "phases": these are build order, not a list of optional/maybe features.**
Everything listed across Phase 1–4 and in section 6 (cross-platform import/export) is
in scope for the product — phasing only controls what gets built first so the coding
agent doesn't try to do everything at once. Nothing here should be treated as
deferrable-indefinitely or cuttable without an explicit decision to cut it.

**Phase 1 (MVP)**: products/variants/inventory export & import, diff preview before commit,
NL bulk edit (single-step), validation with auto-fix suggestions, one-click undo, usable
free tier.

**Phase 2**: collections/discounts/metafields/customers, scheduled jobs, Google Sheets sync,
job history/audit log.

**Phase 3**: store-to-store migration/backup, FTP/SFTP + Drive/Dropbox triggers, public API
+ MCP/AI-agent tool support.

**Phase 4**: full resource parity (orders, payouts, translations, metaobjects), team roles/
approval workflows.

**Cross-platform import/export (section 6) is a required capability, not a stretch goal.**
WooCommerce and BigCommerce support should be scoped alongside Phase 1/2 work (not pushed
to "someday") since it's a core acquisition channel — merchants migrating platforms are a
key entry point to the product.

**Advanced/differentiator features to design for from day one (even if built later)**:
- Multi-step AI operation chains with editable plan preview
- AI catalog health scan (missing alt text, duplicate SKUs, thin descriptions, etc.)
- AI-generated bulk content rewrite (brand-voice learned from examples)
- AI-assisted column mapping on messy/foreign imports
- Pre-commit anomaly detection (e.g., "this would change 4,000 prices by 50%+")
- Visual rule builder as a non-chat alternative, compiling to the same execution engine
- Timeline/version history with per-field revert (not just single-snapshot undo)
- Multi-store bulk operations (agency use case)

## 6. Cross-platform import/export & field mapping

This is a distinct capability from the core Shopify-native bulk edit flow (sections 1–5)
and should be treated as its own module in the architecture, not an afterthought bolted
onto the CSV importer. Matrixify markets this heavily ("migrate from WooCommerce/Magento/
BigCommerce") — merchants moving platforms or running multi-channel operations expect it.

### Named platforms to support (prioritize by merchant volume)

- **Phase 1 target**: WooCommerce, BigCommerce — highest overlap with Shopify's target
  merchant segment (SMB moving off WordPress/legacy carts)
- **Phase 2 target**: Magento (Adobe Commerce), Squarespace, Etsy, Wix
- **Phase 3+ / lower priority**: PrestaShop, OpenCart, Amazon seller feed format,
  Google Shopping feed format (export-only target, not a full platform)

For each platform, support both directions where it makes sense:
- **Import**: bring in a store's existing product/order/customer export from that
  platform, mapped into Shopify's schema
- **Export**: reshape Shopify data into that platform's expected import format (for
  merchants going the other way, or running a second store on another platform)

### Field-mapping architecture

- **Platform profiles**: a config-driven mapping definition per platform/version
  (e.g. `woocommerce-v8`, `bigcommerce-v3`) stored as structured data (JSON in Postgres
  or a dedicated `platform_field_maps` table), not hardcoded per-platform logic —
  this keeps adding a new platform to a data/config change rather than a code change
  wherever possible.
- **AI-assisted auto-mapping**: on upload, detect the source format (by header pattern
  or an explicit platform selector) and pre-fill the field mapping using the matching
  platform profile, falling back to AI inference for unrecognized/custom columns.
- **Manual mapping UI**: always show a side-by-side mapping screen — source column on
  the left, target Shopify field on the right (dropdown, AI-suggested but editable) —
  before any import runs. Never fully hide this step behind "AI did it automatically";
  merchants need to see and correct the mapping, especially for anything ambiguous
  (e.g. a "Type" column that could mean product type or variant option).
- **Save mapping as a reusable template** — once a merchant maps their WooCommerce
  export once, they shouldn't have to remap it for their next monthly sync; ties into
  the "templates/recipes" feature from section 5.
- **Structural differences to handle explicitly**, not just field-name differences:
  variant/option modeling differs significantly across platforms (e.g. WooCommerce
  attributes vs. Shopify options/variants), tax handling, image/gallery structure,
  category vs. collection models, and order status vocab — these need translation
  logic per platform pair, not just a column rename.
- **Validation before commit** applies the same diff/preview + anomaly detection from
  section 5/7 regardless of source platform — cross-platform import is not exempt from
  the trust/safety mechanics that are core to the product.

## 7. Pricing scope

**Model: base tier by store size (catalog/SKU count) + AI credits on top**, sold as a
single monthly subscription per plan. This deliberately avoids Matrixify's pain point
of hard row-count caps per file — merchants shouldn't hit a wall mid-operation just
because their catalog crossed an arbitrary line.

### What's metered vs. always included

- **Never metered, always included on every plan (including free)**: manual export,
  manual import, diff/preview screen, one-click undo, field-mapping UI, saved mapping
  templates, job history. These are the trust mechanics the product is built on — they
  should never feel like an upsell, or it undermines the "safe to use" positioning.
- **Metered by store size (catalog tier)**: how many products/SKUs the account can
  actively manage. This scales the base subscription price.
- **Metered by AI credits (monthly allowance, resets each billing cycle)**: each of the
  following consumes one credit —
  - one natural-language bulk-edit request (regardless of how many records it affects)
  - one AI catalog health scan run
  - one AI-assisted column-mapping pass on a new/unrecognized import format
  - one AI content-rewrite batch (defined as up to ~50 products per credit)
  - Anomaly detection and the plain-English impact summary ride along with whichever
    AI action triggered them — not separately metered.

### Draft tiers (adjust exact numbers/prices during go-to-market planning)

| Plan | Catalog size | AI credits/mo | Scheduled jobs | Cross-platform import/export | Multi-store | Notes |
|------|-------------|----------------|-----------------|-------------------------------|-------------|-------|
| **Free** | up to ~250 products | small monthly allowance (enough for a real trial, not a token amount) | — | manual only, no scheduling | — | Must be usable on a real catalog, not a crippled demo — this is the adoption engine |
| **Starter** | up to ~2,000 products | moderate allowance | weekly | included (WooCommerce/BigCommerce) | — | Entry paid tier for small/growing stores |
| **Growth** | up to ~10,000 products | higher allowance | daily | included, all supported platforms | — | Core paid tier, likely where most revenue concentrates |
| **Advanced/Agency** | unlimited or very high | highest allowance | daily + custom | included | multiple stores | Role-based approval workflows, audit export, priority support |

- **Credit top-ups**: allow buying additional AI credits mid-cycle on any paid plan
  rather than hard-blocking a merchant mid-task when they run out — avoids the
  frustration of a capability wall right when it matters most.
- **Free-tier AI credits should be real, not symbolic** — enough to let a merchant
  genuinely try the NL bulk-edit and catalog health scan once or twice, since that's
  the feature that differentiates from Matrixify and needs to be experienced, not just
  described, to convert someone.
- **Store-size tier, not row-count-per-file**, is the scaling axis for the base price —
  this directly avoids the tier-boundary resentment visible in Matrixify's negative
  reviews (crossing a row threshold mid-file forcing an upgrade).

### Open pricing questions to settle before launch (not architectural blockers)
- Exact price points per tier (competitive with Matrixify's $20/$50/$200 range, or
  positioned differently given the AI-first pitch)
- Whether multi-store (agency) pricing is a flat multiplier per additional store or a
  separate agency-specific plan
- Annual billing discount structure, if offered

## 8. Design/UX standards to follow

- Production-ready code only — no HTML mockups or placeholder UI in the embedded app;
  use Polaris components properly for the embedded dashboard.
- Every bulk operation (AI-generated or manual) must show a **diff/preview screen**
  before committing — this is non-negotiable, it's the core trust mechanic.
- Every commit must be undoable via a stored snapshot.
- Internal admin panel can use a distinct visual style from the merchant-facing app
  (it's a separate audience — ops/support, not merchants) — favor clarity and density
  over marketing polish there.
- Large file/job handling must show live progress, and support pause where feasible.

### 8a. Visual direction — embedded dashboard (merchant-facing)

The embedded dashboard must feel **native to Shopify Admin**, not like a bolted-on
third-party tool. Merchants should be able to move between Shopify's own screens and
ours without a visual seam.

- **Use Shopify Polaris as the actual design system**, not just "inspired by" — real
  Polaris components (`Card`, `IndexTable`, `Banner`, `Badge`, `Toast`, `Modal`,
  `ProgressBar`, `EmptyState`, etc.), Polaris design tokens for spacing/color, and the
  Polaris type scale. This is what makes it feel first-party, not a re-skin exercise.
- **Color**: default to Polaris's neutral surface palette (whites/grays) with Shopify's
  green (`#008060` / Polaris `success`/`primary` tones) used the same way Shopify uses it
  — for primary actions and success states, not decoration. Our own accent color (for
  AI-specific features, so they're visually distinguishable as "the smart part") should
  be a single deliberate accent — not a rainbow of feature colors — introduced only where
  AI is actively doing something (e.g. the NL input bar, the AI-generated plan preview,
  AI badges on suggested fixes).
- **Typography**: Polaris's own type stack (system font stack it ships with) for
  in-app UI — don't introduce a separate display font inside the embedded app, since
  contrast with Shopify's own chrome is exactly what would make it feel foreign.
- **Density**: match Polaris's information density (compact tables, condensed row
  heights for bulk data) — this is a data tool, not a marketing page, so prioritize
  scanability over whitespace-heavy layouts.
- **Empty states and errors**: follow Polaris's own voice — plain, direct, action-oriented
  ("No jobs yet. Import a file to get started." / "This import failed — 12 rows had
  missing SKUs. Review and fix."), never vague or apologetic.

### 8b. Motion & animation — used deliberately, not decoratively

Advanced ≠ busy. Motion should always be earning its place by clarifying state or
building trust in what's about to happen — not ambient decoration. Respect
`prefers-reduced-motion` everywhere.

- **Diff/preview reveal**: animate old→new values as a smooth cross-fade or slide
  transition per changed field when the preview screen loads, staggered slightly row
  by row — reinforces "here's exactly what's about to change," which is the app's core
  trust mechanic.
- **AI plan generation**: while the NL prompt is being parsed into a mutation plan,
  show a live, streaming build-up of the plan (steps appearing one at a time as the AI
  "writes" them) rather than a blank spinner — makes the AI feel like it's visibly
  reasoning, not a black box.
- **Bulk job progress**: animated progress bar with live counters (records processed /
  succeeded / failed ticking up in real time via websocket or polling), not a static
  percentage — this is the single most-watched screen during a large job, worth the
  investment.
- **Undo action**: a satisfying, fast "snap back" animation on revert — reinforces that
  undo is instant and safe, which matters emotionally for merchants nervous about bulk
  changes.
- **Catalog health scan results**: issues animate in as they're found (streamed, not
  all-at-once), each with a subtle severity-colored accent — turns a static report into
  something that feels alive and current.
- **Micro-interactions**: hover/press states on buttons and rows using Polaris's own
  motion tokens/timing curves, so custom animations don't feel like a different
  physics engine than the rest of Shopify Admin.
- Reserve the more expressive animation (streaming plan build-up, staggered diff reveal)
  for the moments that matter most (AI actions, bulk commits) — keep routine navigation
  and table interactions fast and understated, matching Shopify's own restraint.

### 8c. Internal admin panel — distinct, denser, ours

Since this isn't Shopify-embedded, it doesn't need to follow Polaris. Favor a dense,
data-first ops console aesthetic (think monitoring/support tooling) — dark or light
theme is an open choice, but prioritize:
- High-density tables for cross-tenant job monitoring
- Fast filtering/search over decorative layout
- Clear status/severity color coding for support triage (failed jobs, stuck jobs,
  billing issues)

## 9. Additional advanced features worth designing for

Beyond the Phase 1–4 roadmap and the AI feature list already discussed, a few more
worth keeping on the radar as the schema and API are designed (so nothing here is
architecturally blocked later):

- **AI change-impact summary in plain English** before committing a job — e.g. "This
  will update 342 products, increase average price by 8%, and affect 3 collections" —
  a narrated summary layered on top of the raw diff table, for merchants who want the
  gist without reading every row.
- **Slack/email notifications on job completion or failure** — especially for scheduled/
  recurring jobs running unattended (ties into the retention value of automation).
- **Role-based approval for large bulk operations** — e.g. staff can *stage* a bulk
  edit but an owner/admin must approve before it executes above a configurable
  size/impact threshold — useful for stores with multiple staff accounts.
- **AI-suggested next actions after a job** — e.g. after a big price update, suggest
  "Want me to update your Google Shopping feed pricing too?" — turns a single action
  into a guided sequence rather than leaving the merchant to remember related tasks.
- **Exportable audit trail per job** (PDF/CSV) — useful for stores that need change
  records for accounting or compliance purposes.
